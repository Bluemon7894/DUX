# DUX (덕스)

**DUX는 사용자가 AI에게 자신의 이동 상황과 선호를 말하면, 그 조건에 맞는 경로를 찾고 이동 중 상황이 바뀌어도 적절한 대안을 다시 안내하는 맞춤형 이동 서비스입니다.**

`Dux`는 라틴어로 ‘안내자’ 또는 ‘길을 이끄는 사람’을 뜻합니다. [Lewis & Short 라틴어 사전](https://www.perseus.tufts.edu/hopper/text?doc=Perseus%3Atext%3A1999.04.0059%3Aentry%3Ddux)

> “오늘 다리가 아파서 천천히 걸을 거야. 계단은 피하고, 5분 정도 더 걸려도 환승이 적은 길로 가고 싶어.”

DUX는 이 요청을 경로 탐색 조건으로 정리하고, 실제 지도·교통 데이터에 따라 경로를 계산합니다. 버스 지연이나 위치 변화로 현재 경로가 어려워지면 사용자의 조건을 유지한 채 대안을 다시 탐색합니다.

## 프로젝트 배경

대부분의 길찾기 서비스는 출발지와 목적지를 입력하면 예상 소요 시간과 대표 경로를 제공합니다. 그러나 같은 경로라도 이용자의 보행 속도, 계단 이용 가능 여부, 환승 부담, 이동 중 발생한 교통 상황에 따라 실제로 이용하기 편한 정도가 달라집니다.

예를 들어 사용자가 평소보다 천천히 걷는 날에는 정류장까지 이동하는 시간이 늘어 버스를 놓칠 수 있습니다. 버스가 지연되거나 환승 연결이 어려워져도 이용자가 직접 정보를 확인하고 대안을 찾아야 할 수 있습니다.

DUX는 경로를 한 번 제시하는 데 그치지 않고, **사용자가 말한 조건과 이동 중 바뀌는 상황을 함께 고려해 경로를 다시 판단하는 것**을 목표로 합니다.

---

## 해결하려는 문제

사용자가 이동 중 겪는 주요 불편은 다음과 같습니다.

- 안내된 보행 시간이 자신의 실제 속도와 다를 수 있습니다.
- 계단, 긴 환승 통로, 많은 보행량이 사용자에게 부담이 될 수 있습니다.
- 버스 지연이나 운행 변경으로 기존 경로를 이용하기 어려워질 수 있습니다.
- 예상 시간만으로는 현재 경로를 계속 따라갈지, 다른 경로로 바꿀지 판단하기 어렵습니다.
- 여러 조건을 지도 앱의 필터와 설정에 일일이 입력하기 번거롭습니다.

DUX는 사용자가 자연어로 이동 조건을 말하고, 앱이 이를 구조화된 조건으로 바꿔 경로 계산과 재탐색에 사용하도록 합니다.

---

## 제품 목표와 핵심 가치

### 제품 목표

1. 사용자가 말한 이동 조건을 경로 탐색에 반영합니다.
2. 도보·버스·지하철·자전거를 조합한 경로를 비교합니다.
3. 이동 중 중요한 정보가 바뀌면 현재 경로의 실행 가능성을 다시 판단합니다.
4. 대안이 더 적합할 때는 변경 이유와 함께 제안합니다.
5. 예측 도착 시각과 실제 도착 시각을 비교해 정확도를 검증하고 보정합니다.

### 핵심 가치

**DUX는 가장 빠른 경로만 찾는 대신, 사용자가 실제로 이용할 수 있는 경로를 찾고 상황 변화에도 그 조건을 유지합니다.**

### 차별화 방향

DUX의 차별화 방향은 대화형 입력 그 자체에만 있지 않습니다. 사용자가 자연어로 표현한 조건을 실제 경로 제약으로 바꾸고, 이동 중 상황이 변해도 그 조건을 유지해 대안을 다시 계산하는 흐름을 핵심으로 둡니다.

이 설명은 제품 방향을 정의하는 것이며, 시장에 유사한 기능이 전혀 없다는 주장을 뜻하지는 않습니다.

## 주요 사용자와 사용 예시

초기에는 특정 장애나 건강 상태를 추정하지 않습니다. 사용자가 직접 선택하거나 말한 **오늘의 이동 조건**만 반영합니다.

### 예시 1: 보행 속도가 평소보다 느린 날

> “오늘 발목이 불편해서 천천히 걸을 거야. 정류장까지 가는 데 여유 있게 잡아줘.”

DUX는 보행 예상 시간을 늘려 버스를 탈 수 있는지 다시 계산합니다. 탑승 가능성이 낮아지면 다음 버스나 다른 대중교통 경로를 비교합니다.

### 예시 2: 계단을 피하고 싶은 경우

> “계단은 피하고 엘리베이터를 이용할 수 있는 경로로 찾아줘.”

DUX는 계단을 포함한 경로를 제외하거나, 엘리베이터 운영 정보가 확인되지 않은 경로의 신뢰도를 낮춰 표시합니다.

### 예시 3: 빠른 도착보다 환승이 적은 경로

> “최대 5분 더 걸려도 괜찮으니까 환승이 적은 길로 가고 싶어.”

DUX는 추가 허용 시간과 환승 선호를 조건으로 정리해 경로를 비교합니다.

### 예시 4: 이동 중 버스 지연

버스 지연으로 환승 시간이 부족해질 가능성이 커지면 DUX는 현재 경로와 대안을 다시 계산합니다. 조건에 맞는 대안이 충분히 나을 때만 변경을 제안합니다.

## 핵심 기능

### 1. 자연어 이동 조건 입력

사용자는 목적지와 이동 선호를 대화하듯 입력할 수 있습니다.

예시 조건:

- 천천히 걷기
- 계단 피하기
- 오래 걷기 어려움
- 환승 적게
- 도착 시간 우선
- 자전거 이용 가능
- 몇 분 더 걸려도 덜 걷는 경로

자연어에서 추출한 조건이 모호하거나 서로 충돌하면, DUX는 경로를 임의로 정하지 않고 사용자에게 확인하는 것을 원칙으로 합니다.

### 2. 맞춤 경로 탐색

정리된 조건과 교통 데이터를 이용해 경로 후보를 찾습니다. 필수 조건과 선호 조건을 구분합니다.

- **필수 조건:** 계단을 피해야 함, 자전거 이용 불가 등 위반할 수 없는 제약
- **선호 조건:** 환승 최소화, 빠른 도착, 보행량 감소 등 경로 비교에 반영하는 기준

필수 조건은 경로 점수의 일부로만 처리하지 않습니다. 예를 들어 계단 이용이 불가능하다고 선택한 경우, 계단 경로를 단순히 “조금 불리한 경로”로 남겨두지 않고 탐색에서 제외하거나 명확히 이용 불가로 표시해야 합니다.

### 3. 이동 중 경로 재탐색

버스·지하철 운행 정보나 사용자의 위치가 바뀌면 다음을 다시 판단합니다.

- 현재 경로를 계속 이용할 수 있는지
- 정류장 또는 승강장에 도착했을 때 탈 수 있는지
- 환승 연결이 가능한지
- 사용자 조건을 지키면서 더 나은 대안이 있는지

### 4. 추천 이유 설명

경로를 추천하거나 변경하는 이유를 이해하기 쉽게 보여줍니다.

예시:

- “현재 버스 지연으로 환승 시간이 부족해질 가능성이 높아요.”
- “4분 더 걸리지만 계단을 피할 수 있는 경로예요.”
- “버스 도착 정보가 오래되어 예상 시간의 신뢰도가 낮아요.”

### 5. 예측과 실제 이동 기록

사용자의 동의와 서비스 정책에 따라 예측 도착 시각과 실제 도착 시각을 기록합니다. 이 기록은 노선·정류장·경로별 예측 오차를 측정하고 단순 보정하는 데 사용합니다.

## AI와 경로 계산의 역할

DUX는 언어 이해와 경로 계산을 분리합니다.

| 구성 요소 | 역할 |
|---|---|
| **AI 자연어 해석** | 사용자의 문장을 보행 속도, 계단 제한, 환승 선호, 추가 허용 시간 등 구조화된 조건으로 변환 |
| **조건 검증** | 빠진 정보나 서로 충돌하는 조건을 확인하고 필요한 경우 사용자에게 질문 |
| **경로 탐색기** | 실제 도로망·노선·운행 정보를 이용해 후보 경로와 예상 시간을 계산 |
| **실시간 정보 처리** | 교통 정보의 변경을 감지하고 경로 재탐색을 요청 |
| **추천 설명** | 계산 결과에서 경로를 선택하거나 변경한 이유를 사용자에게 설명 |
| **오차 기록 및 보정** | 예측과 실제 결과를 비교해 오차를 측정하고 보정 자료로 축적 |

AI가 존재하지 않는 노선, 도착 시간, 시설 상태를 만들어내지 않도록 합니다. 실제 경로와 시간은 이용 가능한 지도·교통 데이터와 경로 탐색기가 결정합니다.

## 경로 탐색 및 재탐색 흐름

### 최초 경로 탐색

1. 사용자가 출발지·목적지와 이동 조건을 입력합니다.
2. AI가 요청을 구조화된 조건으로 변환합니다.
3. 조건이 불명확하거나 서로 충돌하는지 검사합니다.
4. 경로 탐색기가 이용 가능한 교통 데이터와 지도 정보를 조회합니다.
5. 필수 조건을 지키는 후보 경로를 생성합니다.
6. 각 후보의 예상 도착 시간, 환승, 보행량, 데이터 신뢰도를 비교합니다.
7. 상위 경로와 주요 추천 이유를 사용자에게 보여줍니다.

### 이동 중 재탐색

1. 위치나 교통 데이터에 새 정보가 들어옵니다.
2. 데이터의 시각과 신뢰도를 확인합니다.
3. 현재 경로의 실행 가능성과 예상 도착 시간을 갱신합니다.
4. 필요할 때만 대안 경로를 계산합니다.
5. 대안이 충분히 나은지, 사용자의 조건을 지키는지 확인합니다.
6. 제안할 가치가 있을 때 변경 이유와 대안을 안내합니다.

## 고려 변수

### 사용자 및 위치

- 현재 위치와 위치 오차
- 현재 시각
- 사용자가 지정한 보행 속도 또는 보행 조건
- 계단 이용 여부
- 허용 가능한 보행량 또는 환승 선호
- 자전거 이용 가능 여부

### 보행과 환승

- 보행 네트워크상의 실제 거리
- 정류장·역 출입구·승강장까지의 진입 시간
- 환승 통로의 예상 이동 시간
- 보행 속도에 따른 도착 시각
- 실시간 보행 신호 데이터가 없는 구간의 불확실성

### 대중교통

- 버스와 지하철의 실시간 도착 정보
- 운행 시간과 환승 대기 시간
- 지연·우회·중단 정보(안정적으로 제공되는 데이터가 있는 경우)
- 데이터가 마지막으로 갱신된 시각

### 자전거

- 자전거 이용 가능 경로
- 공유 자전거를 이용하는 경우 대여 가능 수량
- 목적지 인근 반납 가능 여부와 관련 정보
- 실제 제공 데이터가 없는 항목은 추정값이나 실제 값처럼 표시하지 않음

### 예측 신뢰도와 보정

- 데이터 갱신 지연
- 위치 오차
- 해당 경로에서 축적된 예측 오차
- 실제 도착 시각과 예측 도착 시각의 차이

버스 도착 예정 정보에 이미 포함됐을 수 있는 차량 속도나 도로 혼잡도는 중복으로 더하지 않습니다. 데이터 제공 방식이 확인된 경우에만 별도로 반영합니다.

## MVP 범위

### 초기 지역

서울 전체가 아니라 **실시간 교통 데이터를 확보할 수 있는 일부 경로**에서 먼저 검증합니다. 지역과 API 제공처는 실제 데이터 접근 가능성, 갱신 주기, 이용 조건을 확인한 뒤 정합니다.

### 교통수단

- 도보
- 버스
- 지하철
- 자전거

승용차 경로는 초기 범위에서 제외합니다. 실제 연동이 어려운 교통수단은 시연용 데이터와 실제 데이터가 화면에서 혼동되지 않도록 구분합니다.

### MVP에 포함

- 자연어 이동 조건 입력
- AI 조건 변환 및 검증
- 조건을 반영한 경로 탐색
- 버스·지하철 실시간 정보가 바뀔 때 재탐색
- 대안 추천과 추천 이유 표시
- 예측·실제 도착 기록
- 단순 경로별 오차 확인 및 보정
- 정보가 오래되거나 불완전할 때 신뢰도 표시

### 후속 기능

초기 MVP에서는 다음을 핵심 약속으로 두지 않습니다.

- 날씨에 따른 비 피하기 경로
- 실시간 보행자 신호 잔여시간
- 차내 혼잡도와 만차 여부
- 지하철 하차 위치와 빠른 환승 칸
- 상세 경사·노면·보행 안전도
- 엘리베이터 고장 등 모든 시설 상태의 전국 실시간 반영
- 모든 이용자·지역에서 도착 시간 오차 1분 이내 보장

이 항목들은 데이터 접근성과 실제 오차 기여도를 확인한 뒤 우선순위를 다시 정합니다.

---

## 재탐색 시작 기준

아래 수치는 **시제품 테스트를 위한 초기 시작값**이며, 검증된 고정 기준이 아닙니다.

- 현재 경로의 탑승 가능성이 **50% 아래**로 추정되면 대안 경로를 계산합니다.
- 다음 중 하나에 해당하면 사용자에게 변경을 제안합니다.
  - 대안이 현재 경로보다 **3분 이상 빠를 것으로 예상되는 경우**
  - 현재 경로의 탑승 가능성이 **20% 아래로 떨어진 경우**
- 대안에 제시간에 도착할 가능성이 낮거나 이동 조건을 지키지 못하면 추천하지 않습니다.
- 사용자가 같은 제안을 거절하면 **5분 동안 동일한 이유의 제안을 반복하지 않습니다.**
- 다만 운행 중단처럼 기존 경로를 이용할 수 없게 된 중요한 변화는 다시 알릴 수 있습니다.

탑승 가능성은 초기에 이동 시간 추정치와 오차 범위를 이용한 근사값입니다. 실제 기록이 쌓이기 전에는 검증된 통계적 확률처럼 표현하지 않습니다.

## 데이터와 외부 API

DUX는 교통수단과 지역에 따라 서로 다른 데이터 제공처를 사용할 수 있습니다. 특정 제공처나 API를 확정하기 전에 다음을 확인합니다.

- 서비스 지역과 지원 노선
- 버스·지하철 위치 또는 도착 예정 데이터 제공 여부
- 데이터 갱신 주기와 지연 가능성
- 운행 변경·우회·중단 정보 제공 여부
- 자전거 대여·반납 정보의 범위와 갱신 주기
- 인증 방식, 사용량 제한, 상업적 이용 조건
- 데이터 출처 표시나 저장 제한 등 이용 조건

**API 제공처와 기술 스택은 아직 확정하지 않았습니다.** 실제 연동 가능성과 해커톤 일정에 맞춰 선정합니다. 데이터가 없는 지역은 신뢰도가 낮은 정보와 시연용 데이터를 구분해 표시합니다.

## 예측 정확도와 검증

### 목표

- 도착 시간 오차의 **중앙값 1분 이내**를 목표로 합니다.
- 이 목표는 모든 경로와 상황에서 보장하는 약속이 아닙니다.
- 정확도는 실제 이동 기록이 충분히 확보된 제한된 경로에서 검증합니다.

### 측정 지표

- **절대 오차 중앙값:** 예측과 실제 도착 시각의 차이 중 중앙값
- **90백분위 절대 오차:** 큰 오차가 어느 정도 발생하는지 확인
- **예상 범위 적중률:** 실제 도착 시각이 제시된 시간 범위 안에 든 비율
- **재탐색 제안 효과:** 제안된 대안이 실제로 도착 시간을 줄였는지
- **필수 조건 위반 건수:** 계단 제외 등 필수 조건을 위반한 추천 수
- **재탐색 지연:** 주요 교통 상황 변경 후 새 경로를 제안하기까지 걸린 시간

### 오차 기록 방식

가능한 경우 아래 항목을 경로 단위로 기록합니다.

- 경로와 교통수단 조합
- 예측 시각과 예측 시 사용한 데이터 시각
- 실제 도착 시각
- 재탐색 발생 여부와 이유
- 실제로 선택한 경로
- 데이터 누락 또는 지연 여부

초기에는 노선·정류장별 평균 편차 등 단순 보정을 적용합니다. 요일·시간대별 세분화 모델은 데이터가 쌓인 뒤 검토합니다.

## 개인정보 및 안전 원칙

- 건강 상태나 장애를 AI가 추정하거나 진단하지 않습니다.
- 사용자가 직접 입력한 오늘의 이동 조건만 경로 계산에 사용합니다.
- 정밀 위치와 이동 기록은 서비스 제공에 필요한 범위에서만 처리합니다.
- 이동 기록의 저장 목적과 기간을 명확히 하고, 사용자가 동의하지 않으면 개인화 보정에 사용하지 않습니다.
- 시설 운영 상태나 교통 정보가 확인되지 않으면 정상이라고 단정하지 않습니다.
- 예측 시간은 확정된 도착 시각이 아니므로 데이터 시각과 신뢰도 또는 오차 범위를 함께 안내합니다.
- 계단 이용 불가 등 안전과 접근성에 중요한 조건은 점수 가중치가 아니라 반드시 지켜야 할 제약으로 처리합니다.

## 개발 단계

### 1단계: 핵심 경로 흐름

- 서울의 제한된 테스트 구간 선정
- 자연어 입력과 경로 조건 변환
- 조건이 적용된 경로 후보와 예상 시간 표시
- 교통수단이나 API 연결이 어려운 부분은 시연 데이터로 분리

### 2단계: 실시간 재탐색

- 버스·지하철 실시간 정보 연결
- 정보 갱신에 따른 현재 경로 재평가
- 재탐색 기준과 반복 알림 방지
- 대안 추천 이유 표시

### 3단계: 오차 기록과 보정

- 예측 및 실제 도착 시각 기록
- 중앙값·90백분위 오차 측정
- 경로별 단순 오차 보정
- 데이터 최신성과 신뢰도 표시 개선

### 4단계: 교통수단과 접근 조건 확장

- 자전거 대여·반납 정보 연동
- 더 다양한 이동 조건 추가
- 검증 결과에 따라 시설 상태·날씨·혼잡 관련 기능 검토

---

## 제약과 위험 요소

- 교통 데이터의 정확도와 갱신 주기는 지역 및 제공처에 따라 다릅니다.
- 실시간 정보가 늦거나 끊기면 재탐색 결과도 늦거나 부정확해질 수 있습니다.
- 자전거 대여소 재고는 사용자가 도착하기 전에 바뀔 수 있습니다.
- 자연어 입력이 모호하거나 충돌하는 조건을 포함하면 확인 질문이 필요합니다.
- 조건을 더 많이 반영한다고 정확도가 반드시 높아지는 것은 아닙니다. 신뢰할 수 있는 데이터와 실제 검증이 중요합니다.
- MVP의 도착 오차 목표는 제한된 지역·경로에서 측정하며, 다른 지역이나 상황으로 일반화하지 않습니다.

## 프로젝트 상태

현재 프로젝트는 **기획 및 MVP 설계 단계**입니다.

- 서비스명: **DUX (덕스)**
- 핵심 경험: **자연어로 이동 상황을 말하면, 그 조건을 지키는 경로를 찾고 상황 변화에 따라 재추천**
- 초기 범위: **서울 일부 경로, 도보·버스·지하철·자전거**
- 검증 목표: **제한된 테스트 경로에서 도착 시간 오차 중앙값 1분 이내를 목표로 측정**
- 미정 항목: **실제 API 제공처, 기술 스택, 테스트 경로, 개인정보 저장 정책의 구체적 구현**
