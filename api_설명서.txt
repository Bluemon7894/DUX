1. 현재 준비된 것과 아직 구현해야 하는 것
======================================================================

이 자료팩은 API 연결 코드, 인증키, 공식 근거, 정적 참조자료를 모은 개발용 묶음입니다.
현재 Python 예제로 장소검색, 이동수단별 경로, 일부 버스 도착정보, 지하철 운임,
통계, 공개 샘플 등을 조회할 수 있습니다.

index.html은 API와 근거를 읽는 자료 정리 화면입니다. 출발지·목적지를 입력해서
이동 안내를 받는 완성된 길찾기 웹앱 화면은 아닙니다.

프로젝트 전체를 완성하려면 다음 부분을 별도로 연결해야 합니다.
  1) 사용자의 문장을 구조화된 이동 조건으로 바꾸는 AI 처리
  2) 실제 경로 후보와 접근성·운행정보를 결합하는 서버
  3) 조건을 유지하면서 후보를 비교하는 점수 계산과 재탐색
  4) 노트북·태블릿·휴대폰에서 사용하는 반응형 웹 화면
  5) 이동 기록과 실제 도착시각을 수집하는 검증 기능

현재 생성형 AI 모델용 키는 발급되지 않았습니다.
API 응답 성공은 AI 기능이나 도착시간 정확도가 검증되었다는 뜻이 아닙니다.

3. PC에서 실행 준비하기
======================================================================

3-1. Python 확인

PowerShell을 열고 다음을 입력합니다.

  python --version

Python 3.9 이상이 필요합니다. 현재 코드는 Python 표준 라이브러리만 사용하므로
pip install, 가상환경 생성, 추가 패키지 다운로드가 필요 없습니다.

python 명령이 없지만 py 명령이 있다면 다음도 확인할 수 있습니다.

  py --version

py로 실행할 경우 이 문서의 'python'을 'py -3'으로 바꿀 수 있습니다.
예: py -3 -X utf8 -B code/transit_api.py status

둘 다 실행되지 않으면 해당 PC에 Python 실행 환경부터 준비해야 합니다.
이 자료팩에는 Python 설치 프로그램 자체는 포함되어 있지 않습니다.

3-2. 작업 폴더 이동

[그대로 실행 — 이 PC의 현재 경로]

  Set-Location -LiteralPath "C:\Users\User\Documents\Codex\2026-10-24\new-chat\outputs\transit-resource-pack"
  Get-Location

Get-Location 결과가 transit-resource-pack 폴더인지 확인합니다.

  Test-Path -LiteralPath ".\code\transit_api.py"
  Test-Path -LiteralPath ".\credentials.private.env"

두 결과가 True이면 필요한 파일이 현재 작업 폴더에 있습니다.
키의 내용은 출력할 필요가 없습니다.

3-3. 명령의 공통 부분

  python -X utf8 -B code/transit_api.py status

  python          : Python 실행
  -X utf8         : Windows에서 한글 입출력 인코딩을 UTF-8로 사용
  -B              : __pycache__ 같은 바이트코드 캐시 파일 생성을 막음
  code/...py      : 실행할 Python 파일
  status          : 실행할 기능 이름

이후 모든 명령은 transit-resource-pack 폴더에서 실행한다고 가정합니다.

4. 인증키를 어떻게 사용하나요?
======================================================================

4-1. 현재 보유 키는 총 3개

  KAKAO_REST_API_KEY
    카카오 장소검색·대중교통·도보·자전거 경로 조회에 사용합니다.

  KAKAO_JAVASCRIPT_KEY
    웹 지도 SDK에서 지도를 표시할 때 사용합니다.
    Python의 route 명령에 사용하는 REST 키와 역할이 다릅니다.

  DATA_GO_KR_KEY
    공공데이터포털 공통 인증키입니다.
    활용승인을 받은 TAGO·서울 버스·초정밀버스·운임 등 13종에서 사용합니다.

공공데이터포털은 '서비스마다 서로 다른 키가 13개' 있는 구조가 아닙니다.
같은 키를 사용해도 서비스별 활용승인이 필요합니다.
13종의 용도와 상태는 8장 및 API키_한글설명.private.html을 확인하세요.

4-2. 자동 로딩 순서

현재 코드의 로딩 순서는 다음과 같습니다.
  1) 자료팩 상위 폴더의 kakao-api-keys.env
  2) 자료팩 안의 credentials.private.env — 같은 이름이 있으면 1번을 덮어씀
  3) 코드가 지원하는 해당 이름의 프로세스 환경변수 — 값이 있으면 최종 우선

이 통합 폴더의 credentials.private.env에 보유 3개 키가 모두 들어 있으므로
자료팩 밖의 kakao-api-keys.env가 없어도 보유 키를 사용할 수 있습니다.

EX_OPENAPI_KEY는 아직 미발급이고 현재 호출 코드에 연결되어 있지 않습니다.
빈 example 파일에 이름이 있다고 해서 관련 기능이 구현된 것은 아닙니다.

4-3. 키 설정 확인

[그대로 실행 / 외부 API 요청 없음]

  python -X utf8 -B code/transit_api.py status

실제 키가 아닌 true/false만 출력합니다.
보유 3개 항목이 true인지 확인합니다. 미발급 항목은 false가 정상입니다.
status 출력에는 도로공사 키가 포함되어 있지 않습니다.

주의: true는 문자열이 설정되었다는 뜻입니다. 키가 유효한지, 서비스 승인이
완료되었는지, 실제 서버 호출이 성공하는지는 별도 실행으로 확인해야 합니다.

4-4. 나중에 새 키를 받았을 때

credentials.private.env를 메모장이나 코드 편집기로 열고 아래 형식으로 저장합니다.

  SEOUL_OPEN_API_KEY=발급받은_실제_키
  SEOUL_SUBWAY_KEY=발급받은_실제_키

위 두 줄은 형식 예시입니다. '발급받은_실제_키'라는 문구를 그대로 넣지 마세요.
이미 있는 같은 이름의 줄을 수정하고 같은 항목을 여러 번 만들지 않는 편이 좋습니다.
각 키는 다른 서비스의 것이므로 DATA_GO_KR_KEY로 대신 채우면 안 됩니다.
파일 이름이 credentials.private.env.txt가 되지 않도록 확장자를 확인하세요.

키를 브라우저 주소, 명령행 옵션, 채팅, 발표 슬라이드에 직접 붙이지 않아도 됩니다.
예제 코드는 키 파일에서 내부적으로 읽습니다.

5. 가장 먼저 따라 해 볼 실행 순서
======================================================================

각 줄을 하나씩 실행합니다. 1번은 로컬 확인이고 2~6번은 실제 서버 요청입니다.
운행상황·서버상태에 따라 결과 건수와 값은 달라질 수 있습니다.

  1) 키 설정 확인
  python -X utf8 -B code/transit_api.py status

  2) 서울역 장소검색
  python -X utf8 -B code/transit_api.py search --query "서울역"

  3) 서울역 → 서울시청 대중교통 경로
  python -X utf8 -B code/transit_api.py route --origin "서울역" --destination "서울시청" --mode transit

  4) 서울 버스 도착 연결 예제
  python -X utf8 -B code/seoul_bus_example.py --query "서울역"

  5) 서울 지하철 도착 공개 샘플
  python -X utf8 -B code/transit_api.py subway --station "서울" --sample

  6) 서울역0150 → 시청0151 지하철 운임
  python -X utf8 -B code/extra_public_apis.py fare --departure-station 0150 --arrival-station 0151

처음부터 모든 API를 한꺼번에 연결할 필요는 없습니다.
장소검색 → 경로 → 서울 버스 → 지하철 샘플까지 한 개씩 정상 응답을 확인한 뒤
추가 기능을 연결하면 어느 단계에서 문제가 생겼는지 찾기 쉽습니다.

6. 공통 결과 읽는 법: HTTP 200만 보고 성공으로 판단하지 않기
======================================================================

HTTP 응답, API 내부 결과코드, 실제 데이터 행 수를 함께 확인합니다.

  http_status: 200
    서버가 HTTP 응답을 보냈다는 뜻입니다. 내부 인증오류가 있어도 200일 수 있습니다.

  checked_at
    이 Python 프로그램이 조회한 시각입니다.
    버스 위치 수집시각이나 기관이 데이터를 생성한 시각과 같지 않습니다.

  sample_key: true
    공개 샘플을 호출했습니다. 본인 개인키로 전 구간을 조회한 결과가 아닙니다.

  status: "OK"
    카카오 경로 응답에서 확인하는 내부 상태입니다.
    route_count와 resolved_places도 함께 확인합니다.

  code / api_code / headerCd / resultCode
    API 종류별 내부 상태코드입니다. 서로 다른 API에 같은 해석을 일괄 적용하지 마세요.
    이전 확인에서는 서울 버스 headerCd=0, TAGO·운임 등 00,
    초정밀버스 K0, 서울 공개 샘플 INFO-000이 정상 응답이었습니다.

extra_public_apis.py의 state 의미:

  success
    HTTP·API 코드가 정상이고 데이터 행이 있습니다.

  success_zero_rows
    정상 코드지만 데이터가 0행입니다. 해당 시간·조건에 결과가 없을 수 있습니다.

  no_data_api
    제공기관이 '데이터 없음' 코드로 답한 경우입니다. 인증 성공 전체를 보장하지 않으므로
    message와 공식 코드 설명도 확인하세요.

  api_error
    내부 오류코드가 반환되었습니다. 키·승인·인자·제공기관 메시지를 확인합니다.

  unverified_api_status
    HTTP 응답은 받았으나 코드에서 정상 여부를 확인할 수 없었습니다.
    정상 데이터로 단정하지 말고 실제 응답 형식과 명세를 대조해야 합니다.

  row_count       : 받아서 파싱한 데이터 행 수
  shown_count     : 화면에 표시한 행 수
  reported_total  : 제공기관이 응답에 적은 전체 건수

세 값은 서로 다를 수 있습니다. shown_count가 5라고 해서 원본 전체가 5건인 것은 아닙니다.
0행도 '버스 운행 중단'이나 '사람이 없음'으로 바로 해석하면 안 됩니다.

명령이 빨간 오류 없이 끝나거나 종료코드가 0이어도 실제 조회 성공을 보장하지 않습니다.
기본 transit_api.py와 서울 버스 예제는 내부 오류·단계 중단을 출력하고도 정상 종료할 수
있습니다. 확장 코드는 성공/0행/데이터없음은 0, API 오류·정상판정 불가는 2,
입력·요청 오류는 1을 사용합니다. 그래도 실제 state와 내부코드를 함께 읽으세요.

7. 카카오 장소검색·대중교통·도보·자전거 경로
======================================================================

7-1. 장소검색

  python -X utf8 -B code/transit_api.py search --query "서울역"

--query 뒤를 원하는 장소명으로 바꿉니다. 공백이 있으면 큰따옴표로 감싸세요.
응답 documents에서 place_name, address_name, road_address_name, x, y 등을 확인합니다.
카카오 장소 좌표는 x=경도, y=위도입니다. 순서를 반대로 넣지 마세요.

7-2. 대중교통 경로

  python -X utf8 -B code/transit_api.py route --origin "서울역" --destination "서울시청" --mode transit

--origin은 출발 장소, --destination은 도착 장소입니다.
현재 CLI는 두 장소를 각각 검색하고 첫 번째 검색 결과의 좌표로 경로를 요청합니다.
따라서 resolved_places가 실제 원하는 장소인지 반드시 확인하세요.
동명이 장소가 잘못 잡히면 '서울 중구 서울역', '서울특별시청'처럼 구체적으로 입력합니다.

route_count는 반환된 후보 경로 수입니다. routes에는 요약 정보가 들어 있습니다.
walking_distance_m는 도보구간 합계 거리, walking_time_s는 도보구간 합계 시간이며
각각 미터·초로 요약합니다. 그 외 원본 필드는 공식 API 명세를 확인하세요.
guidance는 경로 단계 안내문입니다.

이 CLI는 아직 '다리가 아파', '계단은 피하고 싶어' 같은 자연어 조건을 받지 않습니다.
명령 뒤에 그런 문장을 추가해도 맞춤 경로 필터가 적용되지 않습니다.

7-3. 도보 / 자전거

  python -X utf8 -B code/transit_api.py route --origin "서울역" --destination "서울시청" --mode walk
  python -X utf8 -B code/transit_api.py route --origin "서울역" --destination "서울시청" --mode bicycle

walk는 도보, bicycle은 자전거입니다. 자전거 경로가 있다고 해서 출발지에 따릉이가
있거나 도착지에 반납 공간이 있는 것은 아닙니다. 대여정보와 별도로 결합해야 합니다.
승용차 경로는 현재 작품 범위와 예제에 포함하지 않았습니다.

7-4. 지도 화면에 표시하려면

Python 경로 조회와 브라우저 지도 렌더링은 별도입니다.
KAKAO_JAVASCRIPT_KEY와 카카오맵 SDK를 웹앱에 연결하고 실제 실행 도메인을 등록해야 합니다.
현재 자료팩에서는 JavaScript 지도 렌더링을 검증하지 않았습니다.
이 자료팩에 지도를 자동 실행하는 웹서버나 완성된 웹앱 시작 명령은 없습니다.
설정 메뉴와 공식 문서는 kakao-api-guide.txt를 확인하세요.

9. 서울 버스: 정류소에서 실제 도착정보까지 연결하기
======================================================================

[그대로 실행]

  python -X utf8 -B code/seoul_bus_example.py --query "서울역"

이 명령은 단계별로 필요한 ID를 받아 다음 요청에 전달합니다.
  1) 정류소명 검색
  2) 첫 정류소의 arsId로 해당 정류소 도착정보 조회
  3) 첫 도착 행의 stId·busRouteId·staOrd로 노선별 도착정보 조회

주의: 현재 예제는 검색된 첫 정류소와 첫 노선을 선택합니다.
'서울역' 주변의 모든 정류소를 비교하거나 원하는 방향을 자동 선택하지 않습니다.
selected_public_ids의 정류소명·노선명을 확인한 후 결과를 사용하세요.

주요 결과:
  outcome: success        단계 연결이 데이터 반환까지 완료된 경우
  requests_made           실제 요청 횟수. 단계가 끝까지 진행되면 통상 3회
  selected_public_ids     선택된 정류소·노선 ID
  checks                  각 단계의 HTTP·내부코드·반환 건수

ID 구분:
  arsId       : 이용자가 보는 정류소 ARS 번호. 0으로 시작하면 문자열로 보존
  stId        : 서울 버스 정류소 내부 ID
  busRouteId  : 노선 ID
  staOrd      : 해당 노선 안에서의 정류소 순번
  ord         : 노선 도착 API의 인자명. 이 예제에서는 staOrd를 전달

staOrd를 Python 배열의 0번·1번 인덱스로 대신 넣으면 안 됩니다.
비슷한 이름의 맞은편 정류소, 상행·하행은 다른 ID일 수 있습니다.

기록을 파일로 남길 때:

[값 변경 필요 — 새 파일 이름 사용]

  python -X utf8 -B code/seoul_bus_example.py --query "서울역" --output "data/seoul-bus-my-check-01.json"

--output을 생략하면 결과 요약만 출력합니다.
--output은 기록 파일을 새로 생성하고, 이미 같은 파일이 있으면 덮어쓰기를 거부합니다.
처음부터 기존 data/seoul-bus-live-check.json을 출력 경로로 지정하지 마세요.
파일 이름을 02, 03처럼 바꾸거나 출력 옵션 없이 실행할 수 있습니다.
저장되는 도착 스냅샷도 과거 기록이므로 현재 안내에 재사용하지 마세요.

상대 출력 경로는 PowerShell의 현재 폴더 기준입니다. 코드가 새 부모 폴더까지
만들어주지는 않으므로 기존 data 폴더 안의 새 파일명을 사용하면 됩니다.

10. TAGO: 서울 외 지원도시의 정류소·도착·노선 사용하기
======================================================================

10-1. 먼저 지원 도시 확인

  python -X utf8 -B code/transit_api.py tago-cities

도시명과 citycode를 확인합니다. 기존 확인에서 서울 코드11은 목록에 없었습니다.
서울은 이 자료팩의 서울 전용 버스 예제를 우선 사용하세요.
전국 API라는 이유만으로 서울이나 모든 지자체를 지원한다고 가정하면 안 됩니다.

10-2. TAGO 세부 호출은 Python 메서드로 제공

현재 CLI에는 tago-cities만 있습니다. 아래 코드는 개발자가 Python 코드에서
버스 도착·노선 조회를 연결하는 예시입니다. 별도 CLI 인자가 아닙니다.

[코드 예시 — code 폴더에서 transit_api를 import하는 개발 코드]

  from transit_api import TransitAPI

  api = TransitAPI()
  result = api.tago(
      "arrival",
      "getSttnAcctoArvlPrearngeInfoList",
      cityCode=25,
      nodeId="DJB8001378",
  )
  response = result["data"].get("response", {})
  print(response.get("header", {}).get("resultCode"))

cityCode=25와 nodeId=DJB8001378은 이전 대전 검증에 사용한 예입니다.
새로운 목적지나 도시에는 해당 도시·정류소의 실제 ID를 찾아 넣어야 합니다.

지원 메서드 조합:
  stops  / getCrdntPrxmtSttnList       위경도 주변 정류소
  stops  / getSttnNoList              정류소 번호·명칭 조회
  arrival / getSttnAcctoArvlPrearngeInfoList  정류소별 도착
  routes / getRouteNoList             노선 검색
  routes / getRouteAcctoThrghSttnList  노선 경유 정류소

operation마다 필요한 인자는 다릅니다. data/public-api-catalog.json에서
P19~P21의 parameters와 example을 확인하세요. 임의의 nodeId를 만들지 마세요.

TAGO nodeId와 서울 stId, 경기 stationId는 서로 다른 식별자입니다.
서로 대신 넣지 말고 제공기관별 ID 매핑을 별도로 관리하세요.

11. 추가 API 실행: 초정밀버스·운임·승하차·고속버스·경기 등
======================================================================

11-1. 도움말

  python -X utf8 -B code/extra_public_apis.py --help

기본 --count는 5, 허용 범위는 1~20입니다. 공개 샘플은 최대 5행입니다.
--page는 1 이상입니다. 모든 API가 같은 페이징 구조를 쓰는 것은 아닙니다.
예를 들어 경기 버스 도착에는 이 옵션이 원천 API의 페이지 인자로 전달되지 않습니다.
ALL 지하철 일괄 조회는 전체 응답을 받은 후 표시할 행 수만 제한합니다.

11-2. 초정밀버스 15157601

[그대로 실행 — 공식 예시 지역인 함평군]

  python -X utf8 -B code/extra_public_apis.py precision --mode mst_info --stdg-cd 4686000000
  python -X utf8 -B code/extra_public_apis.py precision --mode ps_info --stdg-cd 4686000000
  python -X utf8 -B code/extra_public_apis.py precision --mode rtm_loc_info --stdg-cd 4686000000

  mst_info     : 노선 기본정보
  ps_info      : 노선 경유 정류소
  rtm_loc_info : 차량 위치
  --stdg-cd    : 대상 지자체의 코드. 예제 코드는 함평군

--response-type은 공식 허용값을 확정하지 못했으므로 보통 생략합니다.
기본 응답이 XML이어도 이 스크립트는 JSON/XML을 구분해 파싱합니다.
모든 지역 차량이 반드시 들어 있는 것은 아니며 속도·방향각 단위도 별도 확인이 필요합니다.

이전 조회의 위치 5행에는 2026-08-12부터 2026-10-24까지의 수집일이 섞여 있었습니다.
최신 API를 호출했다고 해서 모든 행이 현재 위치인 것은 아닙니다.
gthrDt, totDt 같은 원본 시각의 의미를 확인하고 오래된 행은 경로 판단에서 제외하세요.

11-3. 지하철 운임 15143846

  python -X utf8 -B code/extra_public_apis.py fare --departure-station 0150 --arrival-station 0151

0150·0151은 검증 예제의 서울역·시청역 코드입니다. 역명 문자열이 아닙니다.
이 API의 역 코드가 다른 API의 statnId와 같다고 가정하면 안 됩니다.
실제 호출 주소는 fare2/getRltmFare2이며 도착 인자는 arvlStnCd입니다.
요금·거리의 단위는 확보한 필드 명세에서 확인되지 않은 부분이 있어
응답 숫자를 임의로 원·미터로 바꾸지 말고 공식 상세 설명을 대조하세요.

11-4. 역별 승하차 15143845

조회일은 YYYYMMDD 형식이고, 코드상 한국 시간 오늘부터 6일 전까지 허용합니다.
최근 7일 범위 안에서도 기관 집계가 아직 없으면 0행일 수 있습니다.

[그대로 실행 — 한국 시간 어제 날짜를 계산한 뒤 조회]

  $transitQueryDate = python -X utf8 -B -c "from datetime import datetime, timedelta, timezone; print((datetime.now(timezone(timedelta(hours=9))) - timedelta(days=1)).strftime('%Y%m%d'))"
  python -X utf8 -B code/extra_public_apis.py passengers --date $transitQueryDate --station-code 0150 --hour 08

--station-code는 역 코드, --hour는 00~23 형식입니다. 8 대신 08을 넣습니다.
20261023 같은 날짜를 계속 고정하면 나중에는 최근 7일 범위를 벗어납니다.
이 데이터는 이용 인원 통계입니다. 지금 타려는 열차의 칸별 혼잡으로 표시하지 마세요.

11-5. 고속버스 15098516

15. 공식 수치·근거를 발표자료에 사용하는 방법
======================================================================

evidence 두 JSON에 합계 32개 팩트와 13개 출처가 있습니다.
index.html에서 먼저 읽고, 정확한 수치·분모·위치는 JSON을 확인하면 편합니다.

facts의 주요 항목:
  metric       어떤 지표인지
  value/unit   값과 단위
  denominator  분모 또는 조사 대상
  period       조사·집계 시기
  region       지역 범위
  location     원문 표·쪽·문단 위치
  source_ids   sources에서 연결할 출처 ID
  limitations  해석할 때 필요한 제한사항

출처를 쓸 때는 source_ids를 같은 파일의 sources.id와 연결하여 기관명·보고서명·
발표일·원문 URL을 확인하세요. excluded_candidates는 확정 근거가 아닙니다.
도움이 되는 후보나 제외 사유를 정리한 부분이므로 32개 팩트와 섞어 세지 마세요.

원자료의 수치는 문제의 규모와 필요성을 설명합니다.
작품의 실제 효과를 자동으로 입증하지는 않습니다.
예를 들어 디지털 역량지수의 일반국민=100 기준값을 인터넷 이용자 비율로 쓰거나,
이동 불편 응답자 내부 비율을 전체 국민 비율로 쓰면 안 됩니다.

작품의 ETA 오차 중앙값 1분, 탑승확률 50%·20%, 대안 3분 이득은
현재 시제품의 목표·시작 기준입니다. 이미 달성한 공식 성과로 발표하지 마세요.
이동기록과 실제 도착시각으로 별도 검증해야 합니다.

16. 웹앱에 API를 연결할 때의 역할 분담
======================================================================

기본 흐름:

  휴대폰·태블릿·노트북의 웹 화면
    → 여러분의 백엔드 서버
    → 카카오 / 공공데이터포털 / 서울 API
    → 필요한 데이터만 정리하여 웹 화면으로 반환

공공데이터 키와 서버용 REST 키는 백엔드에서 읽습니다.
브라우저 JavaScript에 DATA_GO_KR_KEY나 서버용 REST 키를 그대로 넣지 마세요.
지도 SDK용 JavaScript 키는 별도 역할이며 실제 도메인 설정이 필요합니다.

특히 서울의 일부 검증 API는 공식 HTTP 주소로 확인했습니다.
HTTPS 웹 화면에서 직접 HTTP API를 호출하면 혼합 콘텐츠나 CORS 제한이 생길 수 있습니다.
현재 Python 코드는 서버에서 원천 API를 호출하는 예제입니다.
프런트엔드는 여러분의 백엔드가 제공하는 응답을 받도록 개발하세요.

AI와 교통 데이터의 역할:
  AI : '다리가 아파서 천천히', '계단 제외', '환승 적게'를 구조화된 조건으로 변환
  경로 API : 실제 경로 후보와 원천 시간·거리 제공
  운행 API : 버스·열차 도착과 갱신시각 제공
  시설·보행 자료 : 계단·승강기·환승 동선 판단에 필요한 보조 근거
  여러분의 서버 : 조건 유지, 후보 비교, 결측 처리, 재탐색 제안과 기록

AI가 새로운 버스노선이나 도착시각을 만들어내도록 하지 마세요.
계단 여부를 확인할 자료가 없으면 '계단 없음'으로 통과시키지 말고 '확인 불가'로 표시합니다.

노트북·태블릿·휴대폰 사용:
  - Python 예제는 Python 실행 환경이 있는 노트북에서 실행합니다.
  - 태블릿·휴대폰은 완성할 웹앱의 브라우저 화면으로 접속하는 구조입니다.
  - 폰에 이 자료팩을 복사하는 것만으로 Python 백엔드가 자동 실행되지는 않습니다.
  - 다른 기기의 localhost는 그 기기 자신을 가리킵니다. 노트북 주소와 구분해야 합니다.
  - 실제 공유 주소·포트·방화벽·배포 설정은 백엔드를 만든 뒤 정해야 합니다.
  - 현재 위치 사용은 브라우저 권한과 실행 환경에 따라 달라 별도 검증이 필요합니다.

17. 무료 범위 안에서 실행하기
======================================================================

현재 자료팩 정리 과정에서는 결제수단·유료 증설을 신청하지 않았습니다.
무료라고 해도 호출 한도가 없다는 뜻은 아닙니다.

  - route 명령 1회는 출발지 검색 + 목적지 검색 + 경로 조회로 여러 요청을 사용합니다.
  - 서울 버스 연결 예제는 단계가 끝까지 진행되면 보통 3개 요청을 사용합니다.
  - verify_apis.py는 여러 API를 병렬로 실제 호출하므로 반복 실행하지 마세요.
  - 여러 기기가 같은 화면을 열면 기기 수만큼 원천 요청이 늘 수 있습니다.

웹앱 개발 시 같은 정류소의 요청은 서버에서 합쳐 처리하고 짧게 캐시하는 방법을
검토하세요. 캐시 시간은 원천 갱신주기·사용 조건·실제 신선도를 확인한 뒤 정합니다.
모든 데이터를 무조건 1초마다 요청하지 마세요.

고정된 역 좌표·환승거리 파일은 로컬에서 읽고, 실시간 도착과 분리해 관리할 수 있습니다.
화면에는 '마지막 확인 시각'과 원천 수집시각을 구분해서 표시하세요.
오래되거나 없는 정보는 신뢰도를 낮추고 그 사실을 이용자에게 알려야 합니다.

18. 오류가 나면 무엇부터 확인하나요?
======================================================================

18-1. python을 찾을 수 없음 / 명령으로 인식되지 않음
  python --version과 py --version을 확인합니다.
  사용 가능한 실행기가 py라면 앞부분을 py -3으로 바꿉니다.

18-2. can't open file / 파일을 찾을 수 없음
  Get-Location으로 현재 폴더를 확인합니다.
  Test-Path -LiteralPath '.\code\transit_api.py'가 True인지 확인합니다.
  code 폴더 안에서 실행 중이라면 위 통합 폴더로 한 단계 돌아오세요.

18-3. ModuleNotFoundError: transit_api
  예제 파일을 code 폴더에서 따로 떼어 옮겼는지 확인합니다.
  code 폴더의 파일들을 함께 두고 이 문서의 상대경로로 실행하세요.

18-4. 한글이 깨짐
  명령에 -X utf8을 넣었는지 확인합니다.
  TXT/JSON을 여는 편집기의 인코딩을 UTF-8로 선택합니다.
  PowerShell 출력 저장 시 별도의 인코딩 변환이 생길 수 있으므로, 익숙하지 않으면
  먼저 화면 출력으로 확인하거나 스크립트의 --output 기능을 사용하세요.

18-5. KEY is missing / 키가 false
  credentials.private.env가 자료팩 루트에 있는지 확인합니다.
  파일 확장자, 변수 이름, '=' 다음의 값, 같은 이름의 프로세스 환경변수를 확인합니다.
  키 값 자체를 진단용 스크린샷에 표시할 필요는 없습니다.

18-6. SERVICE_KEY / 인증 / 권한 오류
  status의 true만으로는 해결되지 않습니다.
  data.go.kr에서 해당 데이터의 활용승인이 있는지 확인합니다.
  서울 일반·지하철 전용키를 공공데이터 공통키로 잘못 채우지 않았는지 확인합니다.
  예제는 키를 내부에서 URL 인코딩하므로 이미 인코딩된 키를 여러 번 수동 인코딩하지 마세요.
  승인 직후 제공기관 반영 상태나 기관 장애도 확인하되 성공했다고 가정하지는 마세요.

18-7. HTTP 200인데 결과가 이상함
  6장의 API 내부코드·행 수·sample_key를 함께 확인합니다.
  실시간 정보가 아니라 통계를 조회한 것은 아닌지 확인합니다.

18-8. 결과 0행
  정류소·노선·방향·조회일·운행시간·서비스 제공지역을 확인합니다.
  0행을 곧바로 운행중단·혼잡도0·승강기정상으로 해석하지 않습니다.

18-9. No matching place / 엉뚱한 출발지
  장소명을 구체화하고 search로 먼저 검색합니다.
  route 결과의 resolved_places를 확인합니다.

18-10. --date must be within the latest seven calendar days
  오래된 예시 날짜를 그대로 쓴 경우입니다.
  11-4의 어제 날짜 계산 예제를 쓰거나 한국 시간 최근 7일 안의 날짜를 넣습니다.

18-11. Missing --... / unrecognized arguments / invalid choice
  필요한 인자가 없거나 현재 CLI가 받지 않는 인자를 넣었습니다.
  아래 세 도움말은 네트워크 요청 없이 확인할 수 있습니다.

  python -X utf8 -B code/transit_api.py --help
  python -X utf8 -B code/extra_public_apis.py --help
  python -X utf8 -B code/seoul_bus_example.py --help

  주의: verify_apis.py에는 --help 처리가 없습니다.
  'python code/verify_apis.py --help'라고 해도 도움말이 아니라 실제 호출이 실행됩니다.

18-12. Public sample supports only... / Public sample is limited...
  현재 예제의 샘플 범위를 벗어났습니다.
  역별 도착 샘플은 '서울', 열차위치 샘플은 '2호선', 행 수는 최대5를 사용합니다.
  샘플 범위를 늘려 개인키를 대신할 수는 없습니다.

18-13. Refusing to overwrite existing evidence
  seoul_bus_example.py --output의 파일이 이미 있습니다.
  기존 증빙을 덮어쓰지 않는 동작입니다. 다른 새 파일 이름을 지정하거나 --output을 생략합니다.

18-14. Network request failed / 시간초과 / HTTP 오류
  인터넷 연결, 기관 서버 상태, 키·한도, 요청 인자를 확인합니다.
  예제는 키가 포함될 수 있는 요청 URL을 일부 오류 메시지에서 숨깁니다.
  URL이 안 보인다고 임의로 키를 로그에 출력하지 마세요.
  무제한 재시도 대신 한 번 확인하고 원인을 구분합니다.

18-15. Response exceeds 2 MB
  일반 조회는 요청 건수를 줄입니다.
  subway-bulk의 ALL은 --count를 줄여도 원천 응답 크기가 줄지 않습니다.
  일괄 호출의 실제 규모와 처리 방식을 별도로 검토해야 합니다.

18-16. 저장된 기본 검증 기록이 달라짐
  verify_apis.py를 실행했는지 확인합니다.
  이 스크립트는 실제 API들을 호출하고 아래 두 기존 파일을 덮어씁니다.
    data/live-verification.json
    data/public-sample-snapshots.json
  기존 조사 증빙을 보존하려면 바로 실행하지 말고 출력 위치를 별도 개발본에서 바꾸세요.
  검증 시점이 바뀌면 다른 보고서의 '확인 당시 값'까지 자동 갱신되는 것은 아닙니다.

19. 팀원과 공유·백업할 때
======================================================================

내부 개발용으로 폴더를 옮길 때:
  code, data, evidence와 필요한 키 파일을 함께 유지합니다.
  실제 키를 받는 사람과 보관 장소를 팀 안에서 관리하세요.

외부 공개용으로 공유할 때 제외할 파일:
  credentials.private.env
  API키_한글설명.private.html
  그 밖의 *.private.* 파일과 실제 키가 들어 있는 별도 .env 파일

.gitignore에 비공개 파일 패턴이 있지만 ZIP이나 메신저 첨부를 자동으로 막지는 않습니다.
또한 이미 Git에 추가한 파일은 .gitignore만 바꿔도 자동으로 제거되지 않습니다.
공개 제출 전에는 실제 포함 파일을 확인해야 합니다.

기존 outputs/transit-resources-no-keys.zip은 앞선 정리 시점의 키 제외 묶음입니다.
이후 추가한 비공개 키 안내표나 이 상세 설명서까지 자동으로 갱신된 ZIP은 아닙니다.
최신 작업 기준은 현재 transit-resource-pack 폴더입니다.

이 설명서는 실행법과 변수 이름만 포함하고 실제 키 값은 포함하지 않습니다.
키 안내표를 캡처해서 발표 슬라이드에 넣지 말고 필요한 API 이름·용도만 옮기세요.

20. 해커톤 시연 준비 순서
======================================================================

  1) status로 보유 키 설정 확인
  2) 출발지·도착지를 search로 확인
  3) route로 실제 경로 후보 확인
  4) 사용할 정류소·노선·방향 ID 확인
  5) 서울 버스 또는 해당 지역 API의 도착정보 연결
  6) 역·정류소 ID와 시설·환승 참조자료의 매핑 확인
  7) AI가 구조화한 조건을 화면에 보여 사용자가 해석 결과를 확인하도록 개발
  8) 원천 정보가 없거나 오래되었을 때의 표시 준비
  9) 위치·지연 변화에 따른 재추천과 거절 후 반복 억제 로직 검증
 10) 실제 데이터와 시연용 데이터를 화면에서 구분
 11) API 장애 때는 저장 시각이 적힌 과거 자료임을 명확히 표시
 12) 예측 도착과 실제 도착을 따로 기록하여 효과 검증

시연에서 API 응답이 달라져도 설명할 수 있도록 경로 ID·조회시각·원천시각을 함께 남기세요.
현재 자료팩의 과거 성공 기록을 오늘의 실시간 도착값이라고 제시하지 마세요.

문제가 생겼을 때 가장 먼저 볼 파일:
  실행법             이 설명서 3~6장, 18장
  키·한글 용도        API키_한글설명.private.html
  승인·실호출 상태    data/account-status.json / index.html
  요청 인자·필드      data/public-api-catalog.json
  공식 근거·원문      evidence/ 두 JSON / index.html

이 문서는 현재 자료팩의 실제 CLI와 저장된 검증 기록을 기준으로 작성했습니다.
설명서 작성 과정에서는 새로운 API 요청·키 발급·결제·패키지 설치를 하지 않았습니다.
